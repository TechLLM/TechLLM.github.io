매우 큰 AI 모델의 무게 데이터를 GPU 가까이 둔 대용량 저장장치에 보관하면서, 필요할 때 빠르게 읽어 메모리 부족과 여러 장치 사이의 대기를 줄이는 방법을 연구한다.

**무엇이 문제였나** — 초대형 AI 모델의 무게 데이터는 한 GPU의 빠른 메모리에 들어가지 않는 경우가 많아, 여러 GPU에 나눠 담고 서로 기다리게 된다.
**어떻게 풀었나** — 이 연구는 가중치를 전원이 꺼져도 남는 저장장치에 넣고, 작은 읽기 요청을 큰 묶음으로 합치며, 저장장치 정리 작업은 답을 만드는 흐름과 분리한다.
**그래서 뭐가 좋아졌나** — 여섯 모델을 모의 실험한 결과 읽기와 처리 속도가 개선되고 필요한 GPU 수도 줄었지만, 실제 전용 하드웨어를 만들어 검증한 결과는 아니다.

> 책 한 권의 내용을 가까운 창고에 통째로 보관하되, 지금 필요한 쪽만 여러 장씩 묶어 가져오는 것과 비슷하다. 책을 읽는 동안 창고의 복사·정리 작업은 다른 작업대로 처리해 읽는 흐름을 늦추지 않는다.

## 논문 정보

Geraldo F. Oliveira, Arash Tavakkol, Xiangyu Zhu, Ahmet Caner Yüzügüler et al. · Huawei Technologies Switzerland AG; Huawei Technologies Co., Ltd.; ETH Zürich; HUST · arXiv preprint (arXiv:2608.25062v1) · 2026

## 왜 중요한가

모델을 용량 때문에 억지로 여러 장치에 나눠 담지 않아도 된다면, 필요한 장치 수와 장치 사이의 통신 및 대기 시간을 줄일 수 있다. 다만 논문의 결과는 자체 시뮬레이터에 의존하므로 실제 제품에서도 같은 이득을 얻는지는 별도 검증이 필요하다.

## 핵심 지표

| 지표 | 값 | 설명 |
|---|---|---|
| FLINT 유효 HBF 트래픽 비율 | **90–97%** | MoE 모델에서 FLINT가 읽은 HBF 트래픽 중 실제 계산에 사용된 비율 |
| H3 대비 유효 HBF 대역폭 | **6.2×** | 여섯 모델 평균; MoE 모델의 모델별 범위는 4.0×–14.3× |
| HBM-only 대비 디코드 처리량 | **2.2×** | GPU별 디코드 처리량의 여섯 모델 평균 |
| HBM+SSD 대비 디코드 처리량 | **1,205×** | SSD에 넘긴 가중치를 읽는 단일 GPU 시스템과 비교 |

## 어떻게 동작하나

FLINT는 GPU 연산 코어, 온다이 L2 캐시, HBM, 기존 스테이징 버퍼, HBF를 지나는 다섯 계층을 모델링한 자체 trace-driven 시뮬레이터로 평가했다. HBM 모델은 Ramulator 2.0과 교차 검증했으며 지속 대역폭을 피크의 67.8%–69.9%로 설정했고, 연산 성능은 B200급 가속기와 50% MFU를 사용했다. 가중치 읽기에 관한 연산·메모리·통신·동기화 이벤트는 WSE workload generator로 생성했다. 평가는 DeepSeek-V3, DeepSeek-V4-Pro, Qwen3-235B-A22B, Llama-4 Maverick, Kimi K2라는 다섯 MoE 모델과 dense 모델인 Llama-3.1-405B, 총 여섯 모델을 네 배치 크기 {1, 4, 16, 64}와 네 문맥 길이 {2, 8, 32, 128K}에서 수행했으며 주 결과는 128K 문맥으로 보고했다. MoE의 전문가 분포는 MMLU 프롬프트를 처리하던 실제 GPU 배포에서 수집했다. 기준은 HBM+SSD, 여러 GPU의 HBM-only, 그리고 컴파일러 기반 층 선행 프리페치를 쓰는 H3이다. 통계적 유의성 검정이나 신뢰구간은 제시되지 않았다.

핵심 수식:

```
BDP = BW × t_R = 2 MB
N_burst = C / B = 2^18
block(b) = floor(b / N_pg/blk), page(b) = b mod N_pg/blk
die(s) = floor(s / P), plane(s) = s mod P, s ∈ [0, 512)
t_refresh = t_ERASE + N_pg/blk × t_PROG = 54.2 ms
T_rot ≥ C_plane / BW_prog = 12.5 s
```

BDP는 대역폭과 페이지 읽기 지연의 곱으로, sustained peak 대역폭에 필요한 최소 버스트 크기다. 논문의 1 TB/s와 2 µs 조건에서는 2 MB가 된다. N_burst는 용량 C를 버스트 크기 B로 나눈 논리 버스트 수이며, 512 GB 스택과 2 MB 버스트에 대해 논문은 2^18 및 256 K 항목을 제시한다. b는 논리 버스트 인덱스, N_pg/blk는 블록당 페이지 수, P는 다이당 평면 수(32)다. die(s)와 plane(s)는 각 버스트 조각을 16개 다이, 512개 평면에 배치하는 공식이다. t_refresh는 블록 지우기와 페이지별 프로그램 시간의 합이며 3 ms와 1024×50 µs에서 54.2 ms가 된다. 이 식은 원본 블록을 읽는 1024×t_R 시간을 보수적으로 제외한 값이다. T_rot는 한 평면의 회전 단계에 필요한 최소 시간이며, 모든 N+1개 평면을 한 번 순환하는 데 약 7분이 걸린다.

## 한계와 주의할 점

- 결과는 자체 trace-driven 시뮬레이터에 기반하며 실리콘 구현이나 실제 HBF 스택 측정으로 검증되지 않았다. HBM 부분만 Ramulator 2.0과 교차 검증되었다.
- 가중치가 추론 동안 불변하고 배포 시 정해진 레이아웃으로 한 번 적재된다는 가정에 의존한다. 가중치 갱신이나 임의 쓰기가 필요한 워크로드에는 읽기 전용 FTL을 그대로 적용하기 어렵다.
- 플래시 지연·프로그램 시간·P/E 예산은 모델 설정값이며 실제 HBF 수명 자료가 부족하다. 특히 수명 결과는 10^5부터 10^7까지의 가정한 P/E 범위에 좌우된다.
- phantom-plane은 다이마다 추가 평면을 필요로 한다. SLC 읽기 경로는 페이지당 약 2 GB/s인 반면 프로그램 경로는 약 80 MB/s이므로, 프로그램 큐가 포화되면 전경 읽기에 역압력이 생길 수 있다.
- 전원 차단 후 가중치와 유지보수 상태를 복구하지 않고 새 설치로 취급하므로, 논문이 추정한 재설치 시간인 약 6.7분이 서비스 복구 제약이 될 수 있다.
- dense Llama 3.1-405B에서는 HBM-only보다 토큰당 에너지가 1.64× 증가했다. 따라서 처리량과 GPU 수의 이점이 모든 모델에 그대로 적용되지는 않는다.
- 가중치 접근이 연속된 큰 묶음으로 모이지 않고 요청이 흩어지면, 요청 병합과 평면 병렬 읽기의 이득이 줄어들 수 있다.
- 복사해야 하는 페이지 수가 프로그램 큐의 처리 능력을 넘어서면 큐가 밀리고, 병목이 전경 추론 읽기로 전파될 수 있다.
- 핫 블록의 요구량이 논문에서 측정한 스택당 0.86 GB/s와 16개 phantom-plane의 합산 프로그램 대역폭 1.28 GB/s를 넘어서면 회전 주기와 리프레시 적期内 완료를 보장하기 어렵다.
- 전원 손실 뒤 리프레시 카운터와 배치 상태를 복구하지 못하면 기존 HBF 데이터를 즉시 신뢰해 추론을 재개할 수 없고, 전체 재설치가 필요하다.
- dense 모델처럼 매 토큰 모든 가중치를 순서대로 읽으면 GPU 패키지 수의 이득이 제한되고, 높은 비트당 HBF 읽기 에너지 때문에 총 에너지가 증가할 수 있다.

## 시스템 적용 아이디어

논문의 기법을 비슷한 구조를 가진 시스템에 옮길 때의 적용 지점이다.

### 실제 요청으로 동작하는 HBF 버스트 병합 컨트롤러

HBF 베이스 다이의 읽기 경로에 FLINT의 cache request queue와 cl-to-page mapping 테이블을 둔다. 요청을 물리 페이지·블록 좌표별로 모아 plane-parallel burst로 발행하고, 현재 버스트가 전송되는 동안 다음 읽기를 겹친다. 이 기법은 실행 시점의 요청 순서를 쓰므로 MoE 전문가 선택에 따라 접근 순서가 달라지는 경우에도 컴파일 시점 힌트에만 의존하지 않는다. 적용 전후 재요청 비율과 유효 대역폭을 모델별로 비교한다.

**적용 지점** — 플래시 메모리 컨트롤러의 가중치 읽기 요청 병합·스케줄링 단계

**기대 효과** — 논문 시뮬레이션에서 H3 대비 유효 HBF 대역폭이 여섯 모델 평균 6.2×, MoE 모델에서는 4.0×–14.3× 향상

### 읽기 전용 가중치용 버스트 주소 변환표

모델 적재 단계에서 가중치를 정해진 버스트 레이아웃에 배치하고, 논리 버스트 인덱스를 물리 블록·페이지 좌표로 바꾸는 표를 생성한다. 추론 중에는 이 표를 단일 SRAM 조회로 사용하고, 쓰기 갱신에 필요한 범용 FTL 경로는 제외한다. 모델 배포 도구가 이미지와 주소표를 함께 검증하도록 연결한다. 가중치가 추론 중 변경되지 않는 시스템에 한해 적용한다.

**적용 지점** — 추론용 가중치 이미지의 주소 변환 단계

**기대 효과** — 512 GB 스택과 2 MB 버스트 조건에서 주소표는 256 K 항목이며, 논문은 기존 페이지 단위 SSD FTL보다 512× 적은 항목과 스택당 1.8 MB의 전체 FTL 구조를 보고한다.

### 추론 읽기와 분리된 플래시 리프레시 경로

읽기 경로에 ECC 보정 데이터를 분기해 migration bitmap으로 아직 복사하지 않은 페이지를 판별하고, program queue를 거쳐 phantom plane에 기록한다. 전경 요청이 닿지 않은 페이지는 낮은 우선순위 scrubber가 읽어 채운다. 블록 단위 매핑 갱신과 평면 역할 순환을 함께 구현하고, 프로그램 큐가 밀릴 때의 완료 보장을 점검한다. 추가 평면과 전원 손실 후 재설치 요구사항을 제품 설계에 반영해야 한다.

**적용 지점** — 비휘발성 메모리의 백그라운드 유지보수 및 읽기 경로

**기대 효과** — 논문 시뮬레이션에서 phantom-plane refresh 적용 시 리프레시 없는 동작과 동일한 디코드 처리량을 보였으며, HBF 다이 면적 비용은 3.1%, HBF 베이스 다이 추가 면적은 7 nm에서 3.9 mm²다.

## 단계별 도입 로드맵

| 단계 | 목표 | 액션 | 기대 효과 |
|---|---|---|---|
| Phase 1 | 대상 모델과 메모리 접근 패턴이 FLINT 가정에 맞는지 확인 | 대표 MoE 및 dense 추론 추적에서 가중치 재사용, 요청의 페이지·버스트 집중도, KV cache 용량, 목표 TPOT를 측정한다. | HBF가 용량 문제를 해결할 대상인지, 대역폭이나 에너지에서 불리할 모델은 무엇인지 구분한다. |
| Phase 2 | 버스트 제어와 읽기 전용 주소 변환의 프로토타입 검증 | 컨트롤러 시뮬레이터 또는 FPGA 경로에 요청 큐, cl-to-page 매핑, 버스트 스케줄러, 모델 적재 시 생성하는 버스트 주소표를 구현해 재요청률과 채널 활용도를 계측한다. | 정적 프리페치와 전용 SRAM 버퍼 없이 실제 요청 흐름만으로 성능 목표를 달성할 수 있는지 확인한다. |
| Phase 3 | 리프레시·내구성·서비스 목표를 함께 검증 | phantom-plane 복사, ECC, migration bitmap, background scrubber를 통합하고, 핫 블록 및 전원 차단·재설치 조건에서 TPOT와 리프레시 완료 여부를 검증한다. | 추론 경로에 유지보수 지연을 넣지 않으면서 모델별 가용 용량과 장치 수 목표를 만족하는지 평가한다. |
