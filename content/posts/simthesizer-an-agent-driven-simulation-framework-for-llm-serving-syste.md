새로운 AI 서비스 방식이 나올 때마다 시뮬레이터를 처음부터 고치지 않고, 교체 가능한 부품 구조와 코딩 도우미를 이용해 필요한 기능만 빠르게 추가하는 방법을 제안한 논문이다.

**무엇이 문제였나** — AI 서비스는 도구를 사용하거나 여러 AI 모델을 불러오는 등 점점 복잡해지지만, 기존 시뮬레이터는 한 가지 정해진 흐름에 맞춰져 있어 새 기능을 넣으려면 많이 고쳐야 한다.
**어떻게 풀었나** — 이 논문은 전체 과정을 작은 단계와 연결 관계로 표현하고, 코딩 도우미가 필요한 기능만 추가하게 한다. 실제 기록이나 참고 자료로 결과가 올바른지도 확인한다.
**그래서 뭐가 좋아졌나** — 비교 실험에서 이 구조를 쓴 시뮬레이터는 기존 시뮬레이터보다 실제 처리량을 더 가깝게 예측했고, 시뮬레이션 실행 시간도 더 짧았다.

> 기존 시뮬레이터가 한 가지 길로만 달릴 수 있는 고정 코스라면, Simthesizer는 구간을 이어 새 코스를 만드는 트랙이다. 코딩 도우미가 새 구간을 붙이고, 실제 기록이나 참고 자료에 맞춰 제대로 이어졌는지 확인한다.

## 논문 정보

Wonung Kim, Hyunmin Choi, Minsu Kim, Jaehong Cho, Yeongwook Kim, Jongse Park · KAIST · arXiv preprint (arXiv:2608.24650v1 [cs.AR]) · 2026

## 왜 중요한가

새로운 AI 기능을 실제 장비에 올려 시험하려면 비용과 시간이 많이 든다. 기능을 쉽게 추가하고 교체할 수 있는 시뮬레이터가 있으면, 실제 배포 전에 여러 설계의 성능과 비용을 더 쉽게 비교할 수 있다.

## 핵심 지표

| 지표 | 값 | 설명 |
|---|---|---|
| Simthesizer 확장 평균 처리량 오차 | **2.51%** | 세 기능 확장 과제에서 Simthesizer 확장 결과와 vLLM 실측 처리량의 평균 오차 |
| 기존 시뮬레이터 확장 평균 처리량 오차 | **6.03%** | 동일한 코딩 에이전트와 하네스로 기존 시뮬레이터를 확장했을 때의 평균 처리량 오차 |
| LLMServingSim2.0 대비 평균 시뮬레이션 속도 | **164.9×** | 세 기능 확장 과제에서 Simthesizer의 평균 실행 시간 배수 |
| LLMServingSim2.0 대비 최대 시뮬레이션 속도 | **284.96×** | 세 기능 확장 과제 중 최대 실행 시간 배수 |

## 어떻게 동작하나

Simthesizer simulator는 실행층과 제어층으로 구성된다. 실행층은 계산·통신·논리 노드를 하나의 동적 DAG로 표현한다. 계산 노드는 결정론적·무상태이고, 통신 노드는 링크 경쟁 때문에 비결정적이되 상태를 바꾸지 않으며, 논리 노드는 결정론적·상태FUL하다. 논리 노드가 실행 중 노드를 삽입하고 선후 관계를 다시 연결할 수 있어 실행 엔진 전체를 고치지 않고도 동적 흐름을 표현할 수 있다. 제어층에는 요청 라우팅, 시스템 조정, 배치 스케줄링, 모델 실행, 모델 설명, 계산 시간, 네트워크 시간에 대응하는 7개 인터페이스가 있고, 구현과 정책 상태를 교체 가능한 컴포넌트로 분리한다. 기본 계산 백엔드는 오프라인 프로파일의 보간값을 사용하고, 기본 네트워크 백엔드는 장치-링 연결 그래프 위의 흐름 단위 대역폭을 사용한다. Synthesizer agent는 task-design, sim-mapping, sim-dev의 세 단계로 자연어 요청을 사양 문서, 구현 맵, 검증 보고서로 낮추며, 성능에 중요한 모호한 선택은 사용자에게 확인한다. 실측이 있으면 동일 조건의 내부 신호와 처리량·지연 시간을 비교하는 trace-guided validation을, 실측이 없으면 참고 구현과 선행 연구에 근거하는 reference-guided validation을 수행한다. 평가에서는 동일한 GPT-5.4 xhigh 기반 Codex v0.118.0, 프롬프트, 사양, 하네스 및 프로파일 데이터를 사용하여 FP8 KV cache 양자화, EAGLE3 기반 speculative decoding, hybrid Mamba 지원을 Simthesizer, LLMServingSim2.0, Vidur에 각각 구현했다. SWE-bench와 tau-bench에서는 각각 50~100개 요청을, ShareGPT에서는 400개 요청을 사용했으며 도구 호출은 호스트에서 미리 실행해 지연을 기록한 뒤 시뮬레이션에서 재생했다. 실험 환경은 NVIDIA RTX Pro 6000 Blackwell GPU 2장과 Intel Xeon Gold 6326 CPU였고 실제 서빙에는 vLLM v0.19.1을 사용했다. 투기적 디코딩 사례에는 다섯 번의 합성 실행이 있었으며, 한 실행에서 처음에는 W를 마지막 계층에만 적용해 처리량을 13.4% 과대평가했고 수정 후에는 6.7%의 처리량 차이와 4.7%의 집계 처리량 과소평가를 보였다. 논문은 독립 반복 실행의 평균은 제시하지만 통계적 유의성 검정이나 신뢰구간은 제시하지 않는다.

핵심 수식:

```
K = 2 (사양 예시)
W = min(K + 1, R)
A ∼ p_acc
M = A + 1
child 실행 가능 ⇔ 모든 predecessor 완료
```

K는 예시 사양에서 speculative_width=2로 설정된 draft token 수이다. R은 남은 출력 길이이고, W는 target model이 검증하는 위치 수인 verification width이다. A는 실측 수용 분포 p_acc에 따라 정해지는 수락된 draft 길이이며, M은 요청 상태에 반영되는 committed progress로 A+1 토큰이다. DAG에서는 add_edge로 지정된 선행 노드가 모두 완료된 뒤에만 자식 노드가 실행 가능하다.

## 한계와 주의할 점

- MoE 라우팅은 요청별 실제 expert 선택을 재현하지 않고 프로파일 통계로 추정하므로 데이터·expert 병렬 실행에서 오차가 커질 수 있다.
- TTFT와 ITL은 네트워크 트래픽이나 커널 실행 지연 같은 꼬리 지연 요인의 영향을 받아 TPOT보다 예측 오차가 높게 나타난다.
- 기본 계산 백엔드는 오프라인 측정과 보간에 의존하므로 프로파일 범위를 벗어난 모델·배치·하드웨어 조건의 정확도는 보장되지 않는다.
- 에이전트가 만든 시뮬레이터의 충실도는 사양의 완전성, 참고 근거, 검증 가능한 실제 시스템 측정 여부에 좌우된다. reference-guided validation만으로 실제 시스템과의 일치를 입증할 수는 없다.
- 평가는 두 기존 시뮬레이터, 한 GPU·CPU 구성, 제한된 모델과 워크로드에 집중되어 다른 하드웨어나 시스템 도메인으로의 일반화는 추가 확인이 필요하다.
- 독립 실행의 평균은 제시하지만 오차의 신뢰구간이나 통계적 유의성 검정은 없어 작은 차이의 안정성을 판단하기 어렵다.
- 사양에서 검증 폭 W의 적용 범위를 잘못 정하면 target model의 계산량과 통신량을 과소평가해 처리량을 과대평가할 수 있다. 논문 사례에서는 초기 처리량 과대평가가 13.4%였다.
- 실제 요청별 expert 라우팅 대신 통계적 MoE 라우팅을 사용하면 개별 요청의 부하 분산과 동기화 효과를 놓칠 수 있다.
- 성능에 중요한 조건이 명세에 빠졌는데도 구현을 진행하면, 코드가 실행되더라도 시뮬레이션 의미가 목표 시스템과 달라질 수 있다.
- 실측 데이터가 없는 신규 메커니즘에서는 근거에 맞는 동작인지 점검할 수 있어도 실제 성능과의 차이를 직접 확인하기 어렵다.
- 코드 수정이 컴파일과 기능 테스트를 통과해도 사양의 의미와 다르거나 미지의 회귀가 남을 수 있으며, 하네스 없이는 구현이 너무 이른 단계에서 시작될 수 있다.

## 시스템 적용 아이디어

논문의 기법을 비슷한 구조를 가진 시스템에 옮길 때의 적용 지점이다.

### 확장 사양·구현 매핑·실측 추적을 한 검증 산출물로 연결

Synthesizer agent의 task-design, sim-mapping, sim-dev 단계를 일반적인 시뮬레이터 확장 파이프라인에 적용한다. 사양의 각 성능 가정에 DAG 노드·컴포넌트 구현 위치와 검증 신호를 연결한다. 실행 후 큐 길이, 배치 구성, 자원 이용률 및 최종 처리량·지연 시간의 차이를 해당 결정에 귀속해 기록한다. 차이가 크면 구현 코드를 무작정 바꾸지 않고 사양 또는 매핑 단계로 되돌려 수정한다.

**적용 지점** — 에이전트가 생성한 시뮬레이터 확장의 사양·구현·검증 파이프라인

**기대 효과** — ShareGPT 워크로드와 Qwen3 32B의 speculative decoding 평가에서 하네스 적용 시 처리량 오차가 4.70%에서 2.84%로 감소했다.

### 런타임 제어 결정을 동적 DAG의 검증 가능한 노드로 표현

서빙 시뮬레이터의 실행 엔진에서 요청 도착, 배치 형성, 라우팅을 논리 노드로 나타낸다. 결정이 난 시점에 compute·communication 노드를 추가하고 선행 관계를 연결한다. 예를 들어 prefill과 decode가 다른 장비에서 실행되면 KV 전송 노드를 둘 사이에 삽입한다. 런타임 변경은 Dynamic DAG API를 통해 수행해 실행 엔진 수정 없이 새 흐름을 조합한다.

**적용 지점** — 서빙 시뮬레이터의 요청 스케줄링·라우팅·실행 의존 관계

**기대 효과** — 기능 확장 평균 처리량 오차 2.51%를 보고했으며, 시뮬레이션은 Vidur 대비 평균 6.65배 빨랐다.

### 성능 가정이 미해결이면 코드 생성을 막는 사양 게이트

코딩 에이전트의 확장 작업 시작 전에 대상 구성, 상태 변수, 의존 관계, 지표 경계, 근거 및 근사 범위를 구조화된 사양으로 받는다. 필수 항목이 비어 있거나 서로 모순되면 sim-dev로 넘어가지 않고 질문이나 근거 보완을 요구한다. speculative decoding에서는 검증 폭 W가 어느 모델 계산에 적용되는지 명시하고, 이를 구현 맵과 계산 추적에서 확인한다. 사양과 실행 추적을 함께 보관해 오차 원인을 재현할 수 있게 한다.

**적용 지점** — 코딩 에이전트의 시스템 기능 구현 전 사양 확인 단계

**기대 효과** — 사례의 초기 13.4% 처리량 과대평가는 W를 마지막 계층에만 적용한 의미 오류에서 비롯됐고, 수정 후보는 6.7%의 처리량 차이를 보였으며 집계 처리량을 4.7% 과소평가했다.

## 단계별 도입 로드맵

| 단계 | 목표 | 액션 | 기대 효과 |
|---|---|---|---|
| Phase 1: task-design | 대상 시스템과 성능 질문을 명확히 정의하고 사양을 완전하게 만든다. | 기존 문서, 참고 자료와 시뮬레이터 인터페이스를 조사해 목표 구성, 상태 수명, 의존 관계, 측정 지표, 근사와 그 근거를 사양 문서에 정리한다. 성능에 중요한 선택이 비어 있거나 모호하면 사용자에게 질문하고, 해결된 결정과 적용 한계를 함께 기록한다. | 암묵적 가정으로 인한 잘못된 동작 모델을 줄이고 검증 기준과 사양의 경계를 고정한다. |
| Phase 2: sim-mapping | 기존 시뮬레이터의 조립식 인터페이스에 사양을 매핑한다. | 각 상태 변화와 의존 관계를 담당할 컴포넌트를 지정하고, 필요한 DAG 노드 삽입·재연결과 compute·communication 모델을 구현 맵에 기록한다. 이미 있는 컴포넌트는 재사용하고 부족한 기능만 역할별 구현으로 추가하며, 이후 검증에 쓸 내부 신호도 지정한다. | 변경 범위를 좁혀 확장 코드를 검토하고 다른 구성과 조합하기 쉽게 한다. |
| Phase 3: sim-dev 및 검증 | 매핑대로 구현하고 실측 또는 기술 근거로 동작을 검증한다. | 컴파일 진단, 실행 오류, 테스트 결과와 사양 위반을 확인하며 로컬 코드를 수정한다. 실측이 있으면 동일 조건의 처리량·지연 시간과 큐 길이, 배치 구성, 자원 이용률을 비교하고, 실측이 없으면 참고 구현·선행 결과에 근거한 판단과 남은 불확실성을 검증 보고서에 남긴다. | 수치 차이의 원인을 추적하고 의미 오류와 구현 오류를 구분하여 확장 결과의 타당성과 적용 한계를 확인한다. |
