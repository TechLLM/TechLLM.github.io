AI 코딩 도우미에 기능을 더하는 플러그인들이 시간이 지나며 어떻게 만들어지고 고쳐지는지 살펴본 연구다.

**무엇이 문제였나** — 플러그인은 설명 글, 설정, 실행 파일이 함께 있어 기존 소프트웨어와 같은 방식으로 관리되는지 알기 어려웠다.
**어떻게 풀었나** — 연구진은 수천 개 플러그인의 변경 기록을 모아 어떤 부분이 바뀌고 함께 바뀌는지 살펴봤다.
**그래서 뭐가 좋아졌나** — 특히 기술 설명 글과 실행 파일이 함께 바뀌는 일이 잦아, 둘을 같이 점검할 필요가 있음을 보였다.

> 요리법과 주방 기구를 함께 관리하는 것과 비슷하다. 요리법에서 쓰는 도구 이름이나 순서가 바뀌면, 실제 도구와 맞는지 같이 확인해야 한다.

## 논문 정보

Ahmed Hereiz, Yingzhe Lyu, Hao Li, Bram Adams, Ahmed E. Hassan · Queen’s University, Software Analysis and Intelligence Lab (SAIL), Canada · ACM Transactions on Software Engineering and Methodology (TOSEM) · 2026

## 왜 중요한가

AI 도우미는 설명 글을 읽고 그에 따라 행동하므로, 설명을 고치는 일도 프로그램을 고치는 일만큼 중요할 수 있다. 한쪽만 고치면 안내와 실제 기능이 달라져 잘못된 결과를 낼 수 있다.

## 핵심 지표

| 지표 | 값 | 설명 |
|---|---|---|
| 분석 플러그인 수 | **8,351개** | 1,926개 GitHub 저장소에서 유효한 플러그인을 분석 |
| 플러그인 변경 활동 증가 | **8.8배** | 2025년 10월 2,923건에서 2026년 3월 25,618건으로 증가 |
| Software Engineering 플러그인 비중 | **61.3%** | 전체 플러그인 중 Software Engineering 하위 범주 합계 |
| 스크립트–Markdown 기능 연계 | **78%** | skills 내 스크립트와 Markdown이 함께 바뀐 사례 중 기능적으로 연결된 비중 |

## 어떻게 동작하나

연구진은 GitHub에서 Claude Code 마켓플레이스 저장소를 찾아 별 10개 이상인 1,926개를 선정하고, 8,351개 플러그인과 77,773개 플러그인 변경 커밋을 분석했다. 플러그인의 기능 분류, 구성요소와 파일 형식, 시간에 따른 변경 활동을 살펴보고, Conventional Commits Specification(CCS) 유형이 실제 변경 내용과 맞는지도 표본 커밋 700건을 수작업으로 분류해 검토했다. 구성요소 간 공진화는 병합된 pull request 10,679건에서 연관 규칙의 Support, Confidence, Lift와 카이제곱 검정을 사용해 측정했다. skills 안의 스크립트와 Markdown 동시 변경 사례 323건 중 64건을 사람이 분류하고, 나머지는 LLM으로 분류해 기능적 연결 유형을 확장했다. 이 연구는 실제 시스템의 정확도나 지연 시간을 비교한 성능 실험이 아니라, 저장소 기록을 바탕으로 한 경험적 연구다.

핵심 수식:

```
\mathrm{Support}(X\Rightarrow Y)=P(X\cap Y)
\mathrm{Confidence}(X\Rightarrow Y)=\frac{P(X\cap Y)}{P(X)}
\mathrm{Lift}(X\Rightarrow Y)=\frac{P(X\cap Y)}{P(X)P(Y)}
```

X와 Y는 같은 pull request에서 바뀐 두 구성요소이며, Support는 함께 바뀐 빈도, Confidence는 X가 바뀔 때 Y도 바뀌는 비율, Lift는 그 동시 변경이 각 구성요소의 기본 변경 빈도로 설명되는 수준을 나타낸다.

## 한계와 주의할 점

- 대상은 GitHub에서 별 10개 이상인 Claude Code 마켓플레이스 저장소다. 별 5개와 25개 기준에서도 정성적 결과가 안정적이라고 보고했지만, 신생·저인지도 플러그인의 유지보수 양상은 분석에서 빠질 수 있다.
- 관찰 기간은 2026년 3월까지라, 출시 초기의 급성장 결과를 장기적인 생태계 추세로 일반화하기 어렵다.
- 커밋·pull request 동시 변경은 함께 수정됐다는 사실을 보이지만, 모든 사례에서 한 구성요소 변경이 다른 구성요소 변경을 필수로 만들었다고 증명하지는 않는다.
- 커밋 재분류와 기능적 연결 분류에 LLM을 사용했다. 검증 표본에서 일치도는 보고됐지만, 분류 오류가 전체 결과에 영향을 줄 수 있다.
- 카이제곱 검정은 유의수준 0.05를 사용했으며 다중 검정 보정은 적용하지 않았다. 여러 구성요소 쌍을 동시에 비교한 결과의 해석에 유의해야 한다.
- 스크립트의 입력·출력 형식이나 변수 이름이 바뀌었는데 SKILL.md가 갱신되지 않아 에이전트가 잘못된 사용법을 따를 수 있다.
- Markdown 지침의 문구 변경이 CCS상 단순 docs나 style로 분류되어 실제 기능 변화나 결함 수정이 유지보수 통계에서 가려질 수 있다.
- 에이전트와 커맨드가 서로의 이름이나 호출 규칙을 참조할 때, 한쪽만 이름을 바꾸면 연결이 끊길 수 있다.

## 시스템 적용 아이디어

논문의 기법을 비슷한 구조를 가진 시스템에 옮길 때의 적용 지점이다.

### skill 지침과 실행 스크립트의 인터페이스 동기화 검사

에이전트 플러그인 저장소의 pull request 검사 단계에 적용한다. 논문에서 분석한 skills 내 Script–Markdown 공진화와 기능적 연결 분류를 활용해, 스크립트의 인자·출력·환경 변수 변경을 추출한다. 같은 skill의 SKILL.md에서 해당 사용법과 예시가 갱신됐는지 대조하고, 변경된 스크립트가 있는데 지침이 그대로면 검토 경고를 남긴다. 이는 특히 co-change 사례 중 78%가 기능적으로 연결됐다는 관찰에 근거한 개선안이다.

**적용 지점** — 에이전트 플러그인의 skill 스크립트와 SKILL.md 검토 단계

**기대 효과** — 논문은 동시 변경 사례의 78%가 기능적으로 연결됐다고 보고한다. 이 검사는 인터페이스 설명 누락을 검토 시점에 드러내는 것을 목표로 한다.

### 커밋 라벨과 실제 변경 기능을 나눠 기록하는 분류기

플러그인 저장소의 변경 분석 파이프라인에 적용한다. 논문에서 재분류한 docs, ci, style 사례처럼 라벨만으로 기능을 추정하지 않고, diff가 AI 지침의 기능 추가·결함 수정·설명 변경 중 무엇을 하는지 구분한다. 결과에는 작성자가 붙인 라벨과 diff 기반 분류를 모두 보존하고, 판단 근거 파일을 연결한다. 이를 통해 지침 수정이 단순 문서 작업으로 집계되어 기능 변화가 숨겨지는 일을 줄인다.

**적용 지점** — 플러그인 저장소 커밋 분류 및 변경 대시보드

**기대 효과** — 논문에서 docs 비중은 diff 기반 재분류 후 10.3%에서 1.7%로 바뀌었다. 라벨과 실제 변경 기능을 구분하면 유지보수 통계를 더 의미 있게 해석할 수 있다.

## 단계별 도입 로드맵

| 단계 | 목표 | 액션 | 기대 효과 |
|---|---|---|---|
| Phase 1 | 플러그인 구성요소와 변경 이력을 구조화한다. | 저장소에서 skills의 Markdown·스크립트, commands, agents, hooks와 설정 파일을 식별한다. 변경 파일과 CCS 라벨을 함께 저장하고, 기존 커밋 분류가 실제 diff와 어긋나는 유형을 표본 검토한다. | 플러그인의 주요 산출물과 유지보수 활동을 구성요소별로 확인할 수 있다. |
| Phase 2 | 함께 바뀌어야 할 구성요소 쌍을 검사한다. | 병합 pull request에서 동시 변경 빈도와 Lift를 계산한다. skills의 Markdown·스크립트 및 agents·commands 참조 관계를 우선 점검 대상으로 두고, 파일·호출 이름·입출력 설명의 일치 여부를 자동 검사한다. | 반복적으로 함께 바뀌는 관계를 찾아 동기화 누락을 리뷰 전에 발견할 수 있다. |
| Phase 3 | 변경 검토와 분류를 지속 가능한 검증 단계로 만든다. | pull request에서 지침과 스크립트의 관련 diff를 묶어 리뷰어에게 제시한다. 커밋 라벨이 docs, style, perf, refactor여도 AI가 실행하는 지침의 의미가 바뀌는지 구분하고, 분류 결과와 검사 오류를 사람이 검토할 수 있게 한다. | 행동에 영향을 주는 문서 변경과 구성요소 간 불일치를 더 일관되게 검토할 수 있다. |
